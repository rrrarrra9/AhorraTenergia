\chapter*{Presentación}
\addcontentsline{toc}{chapter}{Presentación}

AhorraTenergia es un proyecto intermodular orientado al desarrollo de un prototipo de gestión energética doméstica. El sistema representa mediante datos simulados la relación entre consumo eléctrico, producción solar, batería, red eléctrica y precio de la electricidad. El objetivo no es actuar físicamente sobre una instalación eléctrica real, sino construir una arquitectura de software y electrónica que permita visualizar, validar y analizar ese comportamiento de forma segura.

Durante el Sprint 1 se establecieron la organización del equipo, el repositorio, el backlog, el tablero de trabajo, la arquitectura inicial y la primera versión de la memoria. El Sprint 1 finalizó posteriormente con su Sprint Review y Retrospectiva documentadas.

Durante el Sprint 2 se construyó el primer incremento funcional del proyecto. Se definió un contrato de datos común, se implementó una API ASP.NET Core, se desarrolló la telemetría simulada con ESP32 y se implementó un dashboard React conectado al Backend.

\important{\textbf{Estado consolidado a 11/11/2026:} el flujo demostrado durante el Sprint 2 es \texttt{ESP32 → ASP.NET Core → React}. La persistencia mediante Supabase PostgreSQL, prevista inicialmente en el flujo completo, se ha trasladado al siguiente Sprint mediante el Issue \#15. La visualización de \texttt{timestamp} como ``Última actualización'' en React se ha trasladado mediante el Issue \#43.}

\chapter{Introducción, problema y objetivos}

\section{Introducción}

AhorraTenergia busca representar de forma comprensible el comportamiento energético de una vivienda que dispone de consumo eléctrico, producción fotovoltaica, batería y conexión a la red. El proyecto se desarrolla como prototipo educativo y utiliza datos simulados para evitar cualquier actuación sobre instalaciones eléctricas reales.

La solución combina una placa ESP32, un Backend ASP.NET Core, un dashboard React y una base de datos Supabase prevista para la persistencia. El Backend actúa como componente central de comunicación y validación.

\section{Problema o necesidad detectada}

En una vivienda con autoconsumo solar, batería y conexión a la red, el origen y destino de la energía cambian a lo largo del día. La producción fotovoltaica puede ser superior o inferior al consumo, la batería puede cargarse o descargarse y la vivienda puede importar o exportar energía a la red.

Además, el precio de la electricidad puede influir en futuras decisiones automáticas. Sin una vista conjunta de estas variables resulta difícil comprender el estado energético de la vivienda y estudiar reglas de gestión.

\section{Usuario objetivo}

El usuario principal es una persona que quiere comprender mejor el consumo energético de una vivienda, especialmente si dispone de paneles solares y batería. El proyecto también tiene un objetivo académico: demostrar la integración entre desarrollo web, Backend, bases de datos y electrónica programable.

\section{Propuesta de valor}

AhorraTenergia centraliza las variables energéticas principales y permite representar de forma visual el estado de una vivienda. La arquitectura está diseñada para evolucionar posteriormente hacia persistencia histórica, reglas automáticas, precios reales, autenticación y otros componentes del producto final.

\section{Objetivo general}

Diseñar, desarrollar y demostrar un prototipo capaz de recibir telemetría energética simulada, validarla, consultarla mediante una API y representarla en un dashboard, manteniendo una arquitectura preparada para incorporar persistencia y reglas de gestión en iteraciones posteriores.

\section{Objetivos específicos}

\begin{enumerate}
\item Definir una arquitectura común para ESP32, ASP.NET Core, React y Supabase.
\item Establecer un contrato de datos único con nombres, unidades y formatos compartidos.
\item Generar telemetría energética simulada desde una ESP32.
\item Implementar una API REST para recibir, validar y consultar mediciones.
\item Representar el estado energético actual en un dashboard React.
\item Representar un histórico básico de consumo y producción solar.
\item Preparar el modelo de datos para su futura persistencia en Supabase PostgreSQL.
\item Mantener trazabilidad mediante Issues, ramas, commits, Pull Requests y documentación.
\item Evitar la exposición de credenciales, tokens, claves privadas o datos personales reales.
\end{enumerate}

\section{Alcance del Sprint 1}

El Sprint 1 se centró en el arranque y planificación inicial del proyecto. Sus objetivos fueron establecer el repositorio, la organización del equipo, el backlog, el tablero Kanban, la arquitectura inicial, el diseño preliminar del dashboard y la primera versión de la memoria técnica.

\section{Alcance del Sprint 2}

El Sprint 2 tuvo como objetivo construir el primer incremento funcional integrado. El objetivo inicial contemplaba el flujo:

\begin{center}
\texttt{ESP32 → ASP.NET Core → Supabase → ASP.NET Core → React}
\end{center}

Durante el desarrollo se decidió aplazar la persistencia en Supabase al siguiente Sprint. Por tanto, el flujo efectivamente demostrado fue:

\begin{center}
\texttt{ESP32 → ASP.NET Core → React}
\end{center}

El Backend almacena temporalmente las mediciones en memoria. Esta decisión permite cerrar un incremento funcional verificable sin presentar como terminada una integración que todavía no se ha implementado.

\section{Convenciones}

\begin{tabularx}{\linewidth}{@{}p{4.2cm}X@{}}
\toprule
\textbf{Elemento} & \textbf{Convención} \\
\midrule

\section{Datos generados por ESP32}

La ESP32 genera los siguientes campos:

\begin{itemize}
\item \texttt{homeId};
\item \texttt{deviceId};
\item \texttt{timestamp};
\item \texttt{consumptionPowerKw};
\item \texttt{solarProductionPowerKw};
\item \texttt{batteryLevelPercent};
\item \texttt{batteryPowerKw};
\item \texttt{gridPowerKw}.
\end{itemize}

Los identificadores utilizados durante las pruebas son:

\begin{verbatim}
homeId   = "home-01"
deviceId = "esp32-01"
\end{verbatim}

\section{Datos gestionados por el Backend}

El Backend incorpora dos valores que no son enviados por la ESP32:

\begin{itemize}
\item \texttt{electricityPriceEurKwh};
\item \texttt{systemMode}.
\end{itemize}

En el incremento actual se utiliza un precio simulado de \texttt{0.18} €/kWh y el modo \texttt{automatic}.

\section{Ejemplo de telemetría ESP32 → Backend}

\begin{verbatim}
{
  "homeId": "home-01",
  "deviceId": "esp32-01",
  "timestamp": "2026-11-05T16:30:00Z",
  "consumptionPowerKw": 2.35,
  "solarProductionPowerKw": 1.80,
  "batteryLevelPercent": 68,
  "batteryPowerKw": 0.40,
  "gridPowerKw": 0.15
}
\end{verbatim}

\section{Interpretación de batería y red}

Para \texttt{batteryPowerKw}:

\begin{itemize}
\item valor positivo: la batería entrega energía;
\item valor negativo: la batería se carga;
\item cero: sin intercambio.
\end{itemize}

Para \texttt{gridPowerKw}:

\begin{itemize}
\item valor positivo: importación desde la red;
\item valor negativo: exportación hacia la red;
\item cero: sin intercambio.
\end{itemize}

\section{API mínima acordada}

\begin{tabularx}{\linewidth}{@{}p{6.0cm}X@{}}
\toprule

\bottomrule
\end{tabularx}

\section{Modelo de datos previsto para Supabase}

El modelo mínimo definido para la futura persistencia utiliza tres entidades:

\begin{itemize}

\item \texttt{energy\_measurements}.
\end{itemize}

Las relaciones previstas son:

\begin{center}
\texttt{homes 1:N devices}\par
\texttt{devices 1:N energy\_measurements}
\end{center}

Este modelo fue definido durante el Sprint 2, pero su implementación real en Supabase se ha aplazado al siguiente Sprint.

\chapter{Implementación del Sprint 2}

\section{Backend ASP.NET Core}

El Backend se encuentra en:

\begin{verbatim}
src/backend/AhorraTenergia.Api/
\end{verbatim}

La API se desarrolló con ASP.NET Core y expone los cuatro endpoints acordados.

\subsection{Modelo de datos}

La clase \texttt{Datos} incluye las propiedades recibidas desde la ESP32 y las propiedades internas gestionadas por el Backend.

\subsection{Almacenamiento temporal}

Las mediciones se almacenan actualmente en una lista en memoria. Se incluyeron mediciones simuladas iniciales para permitir pruebas del estado actual y del histórico.

Este almacenamiento es deliberadamente temporal. No se presenta como sustituto definitivo de Supabase.

\subsection{Validaciones de telemetría}

El endpoint \texttt{POST /api/telemetry} comprueba, entre otros aspectos:

\begin{itemize}
\item que el cuerpo sea un objeto JSON;
\item que existan los campos requeridos;
\item que \texttt{homeId} y \texttt{deviceId} sean válidos;
\item que el \texttt{timestamp} sea interpretable y esté expresado en UTC;
\item que consumo y producción solar no sean negativos;
\item que el nivel de batería esté entre 0 y 100;
\item que las potencias sean valores numéricos finitos;
\item que la ESP32 no intente enviar \texttt{electricityPriceEurKwh} ni \texttt{systemMode}.
\end{itemize}

Cuando una medición válida se registra, la API devuelve \texttt{201 Created}.

\subsection{Estado actual e histórico}

\texttt{GET /api/energy/current} localiza la medición más reciente por \texttt{timestamp}.

\texttt{GET /api/energy/history?limit=20} ordena las mediciones y devuelve las últimas entradas según el límite solicitado. Un límite inválido devuelve \texttt{400 Bad Request}.

\subsection{Estado del servicio}

\texttt{GET /api/health} devuelve una respuesta mínima con estado \texttt{ok}, permitiendo comprobar que el servicio está operativo.

\section{ESP32 y C++}

La parte de ESP32 se encuentra en:

\begin{verbatim}
src/esp32/
\end{verbatim}

Se utilizó PlatformIO con Arduino Framework. La telemetría se genera de forma periódica y respeta los nombres y unidades definidos en el contrato común.

\subsection{Funciones implementadas}

La ESP32:

\begin{itemize}
\item genera consumo eléctrico simulado;
\item genera producción solar simulada;
\item genera nivel y potencia de batería;
\item genera intercambio con la red;
\item obtiene una referencia temporal mediante NTP y genera timestamps UTC;
\item construye el JSON de telemetría;
\item muestra información de prueba por puerto serie;
\item envía peticiones HTTP a \texttt{POST /api/telemetry};
\item gestiona errores básicos de comunicación sin bloquear permanentemente el programa.
\end{itemize}

\subsection{Pruebas en entorno y placa física}

El desarrollo se comprobó tanto en entorno de simulación como con una ESP32 física. Durante la integración con el Backend se observaron respuestas HTTP \texttt{201}, lo que confirmó que la API aceptaba las mediciones enviadas.

Posteriormente, \texttt{GET /api/energy/current} permitió recuperar la medición más reciente recibida desde la ESP32.

\subsection{Seguridad de configuración}

La configuración local sensible se mantiene fuera del repositorio. El archivo local utilizado para secretos no debe versionarse y está contemplado por las reglas de exclusión del proyecto.

\section{Dashboard React}

El Frontend web se encuentra en:

\begin{verbatim}
src/web/
\end{verbatim}

Está desarrollado con React y Vite.

\subsection{Información mostrada}

El dashboard representa:

\begin{itemize}
\item consumo eléctrico;
\item producción solar;
\item nivel de batería;
\item potencia de batería;
\item intercambio con la red;
\item precio eléctrico simulado;
\item modo del sistema;
\item histórico de consumo y producción solar.
\end{itemize}

\subsection{Estados de interfaz}

Se contemplan cuatro estados:

\begin{itemize}
\item carga;
\item datos disponibles;
\item error;
\item ausencia de datos.
\end{itemize}

\subsection{Comunicación con la API}

El servicio \texttt{energyService.js} permite trabajar con datos mock o con la API. Para el modo API consulta:

\begin{verbatim}
/api/energy/current
/api/energy/history?limit=20
\end{verbatim}

Vite dispone de un proxy de desarrollo hacia el Backend local. La configuración puede documentarse mediante variables como:

\begin{verbatim}
VITE_ENERGY_SOURCE

\chapter{Seguridad y decisiones técnicas}

\section{Principios de seguridad aplicados}

Durante el desarrollo se mantiene la regla de no versionar:

\begin{itemize}
\item contraseñas;
\item tokens;
\item API keys;
\item cadenas de conexión privadas;
\item datos personales reales;
\item archivos de configuración local que contengan secretos.
\end{itemize}

Cuando es necesario documentar variables de entorno se utilizan archivos de ejemplo sin credenciales, como \texttt{.env.example}.

\section{Separación de responsabilidades}

La arquitectura establece que React y ESP32 no deben acceder directamente a Supabase. El Backend ASP.NET Core actúa como mediador central.

Esto permite concentrar en la API las validaciones, el enriquecimiento de datos y, en futuras iteraciones, el acceso a persistencia y las reglas de negocio.

\section{Limitaciones deliberadas del prototipo}

El sistema actual:

\begin{itemize}
\item no controla relés ni elementos eléctricos reales;
\item no conmuta físicamente entre red, solar y batería;
\item no utiliza todavía precios eléctricos reales;
\item no implementa autenticación;
\item no implementa todavía la aplicación Android;
\item no persiste todavía en Supabase;
\item trabaja con una vivienda y un dispositivo de prueba.
\end{itemize}

Estas limitaciones forman parte de la estrategia de desarrollo por incrementos.

\chapter*{Conclusión}
\addcontentsline{toc}{chapter}{Conclusión}

El Sprint 1 permitió establecer la organización, documentación y arquitectura inicial de AhorraTenergia. Posteriormente, la Sprint Review y la Retrospectiva permitieron cerrar formalmente esa fase y detectar mejoras en el procedimiento de revisión y en el registro de evidencias.

El Sprint 2 transformó parte de esa planificación en un incremento funcional. El equipo definió un contrato común de datos, implementó una API ASP.NET Core, desarrolló la generación de telemetría con ESP32 y construyó un dashboard React conectado al Backend.

El resultado demostrado es el flujo:

\begin{center}
\texttt{ESP32 → ASP.NET Core → React}
\end{center}

La persistencia mediante Supabase no se completó durante el Sprint 2 y se mantiene abierta en el Issue \#15. Del mismo modo, la visualización del timestamp en el dashboard se ha separado en el Issue \#43. Esta decisión mantiene la documentación alineada con el estado real del proyecto y evita presentar como terminadas funcionalidades pendientes.

El siguiente incremento deberá centrarse principalmente en implementar la persistencia en Supabase, adaptar el Backend para almacenar y recuperar los datos desde PostgreSQL y completar los ajustes menores del dashboard. A partir de esta base podrán incorporarse progresivamente nuevas funcionalidades como autenticación, precios reales, reglas de gestión, múltiples viviendas y aplicación Android.
